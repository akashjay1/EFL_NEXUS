## Deployed components

- `device-enroll`: project publishable key plus an expiring, one-time enrollment code. The Windows account generates and securely saves its credential ID and 256-bit secret **before** claiming. Retrying with exactly those values is safe after a lost response.
- `device-telemetry`: publishable key plus `x-device-id` (credential UUID) and `x-device-secret`. Credentials are hashed in an unexposed schema. Every request checks the credential, device revocation and session ownership.
- `admin-control`: a verified Supabase user JWT, MFA (`aal2`), a live Auth session and current administrator membership. Owner-only operations reserve/revoke administrators; ordinary administrators can manage enrollments/devices.
- RLS-protected dashboard data and `nexus_current_snapshot()`.
- Private `nexus:monitoring` Realtime broadcasts contain only `{refresh:true}`. They carry no names, device IDs or session records. Clients refetch through RLS; channel authorization caching therefore does not disclose records after access removal.
- `nexus-monitoring-maintenance` runs every minute through `pg_cron`. It records disconnections once per outage, deletes ended sessions after the configured 90-day history period, and expires old enrollment records. It does not fabricate crash end times.

The three files in `supabase/migrations/` match the **actual remote migration versions** returned by Supabase MCP. They were initially generated by the official CLI and renamed to match MCP's applied versions. The old `001_operator_presence.sql` is marked superseded and must not be applied.

## Request contracts

All function requests are POST JSON, at most 64 KiB, with bounded read and database timeouts. Redirects should be rejected by desktop clients. Never log request bodies or credential headers.

Enrollment body: `enrollment_id`, `code`, `installation_uuid`, `credential_id`, `secret`. Codes expire after ten minutes. They are bound to an installation UUID; repeated registration cannot create a second device record. Separate Windows accounts receive separate credentials on that device. Re-enrollment should revoke the previous account credential explicitly when replacing it.

Telemetry body: `session_id`, `events`, optional `live`.

- Up to 50 events per batch, also subject to the total body-size limit.
- Event: `id`, `sequence`, `type`, UTC `timestamp`, `payload`.
- Start sequence is 1; following event sequences must be contiguous. Duplicate IDs with identical contents are acknowledged without inserting history. Conflicting IDs, unordered batches and writes after a terminal event are rejected atomically.
- `started` payload: `operator_name`, `identity_source`, `device_name`, `module`, `app_version`.
- `operator_changed`: `operator_name`, `identity_source`. Initial session identity remains immutable; a new identity period records the change.
- `module_changed`: `module`.
- `closed` / `unclean`: empty payload. `unclean` has an estimated end marker.
- `recording_gap`: positive `dropped_events` count.
- Live update: independently increasing `sequence`, current UTC `sent_at`, integer `idle_seconds`. Historical events do not update liveness. Ordinary heartbeats create no history event.
- Device timestamps older than seven days, more than five minutes in the future or decreasing within a session are rejected. Desktop integration must handle clock errors visibly and reconcile its outbox rather than silently discard history.
- A live update older than two minutes is rejected. Live writes are throttled to half the configured heartbeat interval; each credential is limited to 60 requests/minute.

Identity sources are exactly `KPI Profile` and `Device Fallback`. Fallback identity must equal the session's device-name snapshot. Validated KPI names remain self-reported labels, not proof of the human operator's identity. No KPI codes, portal passwords or documents are accepted.

Successful ingestion returns accepted event count, server event/live sequences and server time. The desktop must use the returned high-water mark when recovering a queue gap; it must not discard events and leave unexplained sequence holes. A fresh application process always uses a new session UUID. Reconnection of the same process keeps its session UUID.

Error responses expose only stable codes: 400 invalid request, 401 missing authentication, 403 denied, 409 state conflict, 429 rate limit and 503 unavailable. Response bodies, database errors and secret values are never logged by the handlers.

Administrator actions: `reserve_admin`, `cancel_invitation`, `revoke_admin`, `list_admins`, `create_enrollment`, `revoke_device`, `revoke_credential`, `device_credentials`. Requests contain only `action` and the validated `args` for that action. A newly created enrollment code is returned once. If its response is lost, inspect state and create a replacement; installation uniqueness prevents duplicate devices.

## Browser and backend configuration

The SDK is pinned to `@supabase/server@1.9.2`, with `deno.lock` included in each deployed artifact. It resolves server-side keys from Supabase's managed environment. No service/secret key is present in these source files, desktop code or public configuration.

Set the Edge Function secret/environment value `NEXUS_ADMIN_ORIGINS` to a comma-separated list of exact approved dashboard origins before browser management calls. No origin is assumed while the dashboard has not been hosted. Requests with an unapproved browser origin fail closed; the desktop endpoints reject browser origins altogether. RLS, not CORS, authorizes record reads.

The current MCP surface provides no Auth-settings or Edge-secret update tool. Those settings remain an explicit dashboard setup step, not a claimed automated change.

# Reconciliation job monitoring

`device-jobs` accepts at most 50 job records per request from an enrolled desktop,
using the same application key and device credential headers as telemetry. It
validates fields before calling the service-only `nexus_ingest_jobs` RPC. Failed
job uploads do not stop operator/session telemetry. The monitoring worker retries
the latest in-memory console snapshot every 30 seconds while connected.

The console supplies portal status and observation time. Assigned names come
from submitted User KPI records matched by job ID and warehouse, never from the
reporting machine's current operator. No KPI user codes or credentials are sent
in job records. Empty assigned names are displayed as **Unassigned** on the web.
The desktop waits for its first successful KPI assignment read before uploading
jobs, so loading/offline assignment data is not mistaken for an unassigned job.

Migration `20261104104646_reconciliation_job_monitoring.sql` adds per-device job
observations with RLS and a read-only admin/AAL2 RPC, `nexus_reconciliation_jobs`.
The RPC selects the newest portal observation for each job/warehouse, excludes
revoked devices, and returns observations from the last seven days. Old uploads
cannot replace a newer observation for the same device/job/warehouse. Jobs that
disappear from a portal list remain last-known observations until they age out;
absence alone is not treated as completion or removal.

The dashboard's **Reconciliation Jobs** tab supports search, status and assignment
filters and displays the portal observation timestamp and reporting device.
Open the reconciliation console in an updated desktop app to populate this feed.
An existing frozen executable must be rebuilt/distributed to send jobs; deploying
only the website and Edge Function does not update installed desktop applications.

Validation performed: dashboard production build and 45 existing dashboard tests;
75 existing Python KPI, monitoring, bridge and focused console checks; seven
existing protocol checks; live database RLS/grant inspection and HTTP rejection
checks for anonymous reads and browser-origin desktop requests. The SQL parser
script requires the currently missing `pgsql-parser` dependency; the migration
was instead applied successfully and its live permissions queried in Supabase.
